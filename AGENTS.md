# AGENTS.md

Project-specific rules for anyone (human or agent) working in this repo. These
were written by the setup skills that bootstrapped the automation; keep them in
sync with the workflows they describe.

## Repository hygiene

- The trunk is `master` and it is protected: squash-only merges, no direct
  pushes, no force-pushes, delete branch on merge.
- Security handling lives in SECURITY.md — private advisories only. Never open a
  public issue or discussion for a security bug.
- Dependency updates arrive as Dependabot PRs (weekly, grouped minor/patch).
  Do not bump dependencies manually unless the bot is disabled for a reason
  stated in the PR.
- Directory ownership lives in CODEOWNERS — route review requests through it.
- SECURITY.md, CONTRIBUTING.md, and the issue forms are the contract with
  contributors — update them in the same PR that changes the behavior they
  describe.

## CI contract

- After cloning, run `lefthook install` once. The pre-commit hook runs
  lint/format on staged files; without it, CI is the only gate.
- Required checks are the `gate`, `commitlint`, and `title-lint` jobs. Do not
  rename CI jobs without updating branch protection — a renamed job silently
  stops being required.
- E2E runs post-merge and nightly, not on PRs. A red e2e after merge is fixed
  on the trunk; do not wait on it in a PR.
- Runner images: CI runs on `ubuntu-latest`. It is pinned deliberately — this is
  a web app with no Apple-platform or Windows-specific code, so the matrix axis
  is the Node version (22, 24), not the OS. Bumping the image is a decision
  about OS coverage, not routine maintenance.
- New third-party actions in workflows require a maintainer's approval —
  workflow files are supply-chain surface. The repository allowlist currently
  permits `actions/*`, `github/*`, `pnpm/*`, `orhun/*`, `softprops/*`; adding an
  action from another owner means updating
  Settings → Actions → General → Allow select actions first.

## Commits and releases

- Commits follow Conventional Commits (feat, fix, docs, style, refactor, perf,
  test, build, ci, chore, revert), enforced by commitlint on the commit-msg
  hook and in CI. PR titles follow the same rules — squash merge uses the title
  as the commit message.
- The changelog is generated by git-cliff at release time and published in the
  GitHub Release notes (plus a `changelog-<tag>` workflow artifact). It is not
  committed to `master`: branch protection rejects the bot's push, and a
  changelog pull request cannot work either because events created with
  `GITHUB_TOKEN` never start workflow runs, so such a PR could never satisfy
  the required checks. Never hand-edit a release note.
- Tags and releases are created by the release workflow only. Never create,
  move, or delete tags manually; `v*` tags are protected by a ruleset. Do not
  "simplify" the workflow back into a direct push to `master` — branch
  protection rejects it with GH006.

## Working agreement

- Keep the local gate green: `pnpm biome check .`, `pnpm tsc --noEmit`,
  `pnpm vitest run`.
- One concern per branch, branch name `<type>/<description>`, PR against
  `master`.
- Branch protection requires 0 reviews (single-maintainer repo) but
  `enforce_admins` is on, so even an admin cannot merge a red PR.
